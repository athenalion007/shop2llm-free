2026-11-06 — version 1.10.1 (Self-Hosted Update Channel) — GitHub distribution channel launch; wordpress.org installs are completely unaffected

* New - Self-hosted update channel: GitHub-channel zips carry a selfhost-channel.php marker plus an "Update URI" header, activating a cloud update checker (mirrors the Shop to LLM Pro pattern — pre_set_site_transient_update_plugins injection, plugins_api details modal, 6-hour negative cache) so installs that cannot reach wordpress.org still receive every release from shop2llm.com. 2026-11-05 — version 1.9.0 (Official AI Stack Nativization + MCP 2026-07-28) — first plugin of its class to follow the official WordPress AI stack posture (competitors all keep self-built endpoints only)

* New - Abilities API registration: the ten MCP tools are mirrored 1:1 as read-only WordPress abilities in the shop2llm namespace (category "shop2llm", input_schema from the existing tools/list JSON Schema, output_schema object, execute_callback delegating to the same shop_to_llm_tools_call implementations, permission_callback __return_true — transport layer gates access). Registered on wp_abilities_api_categories_init / wp_abilities_api_init which only fire when the Abilities API plugin is active, so there is no hard dependency and no Requires Plugins header. meta.mcp.public=true + mcp.type=tool opts each ability into the official MCP Adapter's default server; meta.annotations declare readonly=true / destructive=false / idempotent=true. No tool count change: 10 tools stay 10 (free tier untouched)
* New - Official-stack detection and ceding: shop_to_llm_official_mcp_stack_active() = function_exists('wp_register_ability') && (did_action('mcp_adapter_init') || class_exists('\WP\Mcp\McpAdapter')). When active, the built-in /wp-json/shop2llm/v1/mcp REST route is NOT registered (the adapter's default server at /wp-json/mcp/mcp-adapter-default-server serves the abilities) so the same capabilities are never double-served; without the official stack the built-in endpoint works exactly as before. shop_to_llm_mcp_endpoint_url() helper centralizes the choice and all twelve hardcoded endpoint references were converted (/.well-known/mcp discovery, llms.txt, agents.md, llms-full MCP section, get_store_overview, ACP catalog, settings page cards, hero test, health checklist)
* New - MCP 2026-07-28 support on the built-in endpoint: server/discover (spec-required, returns resultType=complete, supportedVersions, capabilities, serverInfo in _meta, LLM instructions, ttlMs/cacheScope); per-request version negotiation reading params._meta["io.modelcontextprotocol/protocolVersion"] or the MCP-Protocol-Version header, answering UnsupportedProtocolVersionError (-32022) with the supported list for unknown versions; MCP-Protocol-Version response header on success and version-error paths. Legacy clients (no _meta, no header) are served statelessly exactly as before — dual-era per spec
* Fix - Hero "Test MCP" self-test: with the official stack active it verifies locally (counts shop2llm/* abilities via wp_get_abilities) instead of probing the retired endpoint; without the stack the live JSON-RPC initialize handshake is unchanged

2026-11-05 — version 1.8.0 (Output Permission Hardening + Content-Signal 3+1) — security remediation release modeled on the Website LLMs.txt 8.5.4-8.6.0 incident classes

* Security - Logged-out visitor rendering for every AI-facing content read: new shared helper shop_to_llm_public_content_html() renders a post through the full the_content filter chain with wp_set_current_user(0) for the duration (original user restored in a finally block), so membership/paywall plugins that hide protected sections for anonymous users behave identically when the catalog is built — including the realistic case of an admin triggering generation (View /llms.txt click, one-click regenerate, cloud proxy callback with an authenticated cookie), which previously built the cache with admin-visible content. Callers converted: /llms-full.txt post+page blocks (was raw $post->post_content), MCP get_product non-Woo description + excerpt fallback (was raw post_content), MCP search_products non-Woo excerpt fallback, per-page .md mirror body + generated frontmatter description for non-product types (products stay raw — public catalog data by definition, and the_content filters can expand commerce shortcodes unpredictably). Same incident class Website LLMs.txt fixed across 8.5.4-8.6.0; readme gains a verifiable claim FAQ ("Can Shop2LLM expose my members-only content to AI?")
* Security - Password-protected posts excluded from all AI outputs: has_password=false added to the /llms.txt posts query, /llms-full.txt posts+pages queries, MCP get_store_overview latest_posts and the .md slug resolver; get_product and the .md path resolver additionally reject any resolved post with a non-empty post_password (password-protected posts carry post_status=publish, so status-only checks passed them straight through with title, URL and full content). MCP search already had has_password=false — contract now uniform across every output face
* Security - Output escaping audit (no changes required, verified): llms.txt/llms-full.txt titles esc_html + URLs esc_url + prices html_entity_decode'd plain text, MCP payloads via wp_json_encode, /product-feed.xml esc_xml with per-line phpcs exemptions, robots.txt static strings + home_url, policy JSON-LD configuration values only; includes/*.php contain no post_content/post_excerpt reads
* New - Content-Signal 3+1: the opt-in AI usage policy's machine-readable line gains the fourth "use" field from Cloudflare's July 2026 Content Signals extension — open → ai-train=yes, search=yes, ai-input=yes, use=full; attribution → ai-train=no, search=yes, ai-input=yes, use=reference; closed → ai-train=no, search=no, ai-input=no, use=immediate (semantics per developers.cloudflare.com: immediate=interact but store nothing, reference=index/excerpt/link back, full=summarize and reproduce; verified against contentsignals.org and Cloudflare docs 2026-11-05). Still opt-in via the existing policy select (default off), still emitted through the priority-1 robots_txt banner; robots.txt card copy and the readme crawler-controls FAQ updated to say declarative-preference-not-enforcement in plain terms

2026-10-17 — version 1.7.0 (Markdown Mirrors + ACP Readiness + IETF MCP Discovery + Content Signals)

* New - Markdown mirrors for AI coding agents: every published post, page and product is additionally readable at <permalink>.md (e.g. /my-post.md) and any singular URL negotiates to clean Markdown when the client sends Accept: text/markdown (Claude Code, Copilot workspace, Cursor and OpenCode list that media type in HTTP_ACCEPT; browsers never do, so negotiation can only trigger for machine clients). Delivery rides the proven v1.5.4 parse_request URI-fallback lane (priority 99, wins the race against plugin rewrite collisions; /agents.md excluded from the .md pattern; non-matching paths return control to WordPress untouched). shop_to_llm_html_to_markdown() converts via DOMDocument with a recursive walker (headings, paragraphs, lists, tables, links, images, strong/em/code/pre/blockquote/hr; script/style/nav/footer/aside/form/iframe and friends stripped; unknown tags fall through as transparent containers) — dependency-free by design, zero bundled libraries. Output is YAML frontmatter (title, author, published/modified ISO-8601, lang, description, permalink, categories, tags — scalars emitted via wp_json_encode so quoting is correct; product posts add price, currency, availability, sku, gtin) plus the converted body and a Price & Availability section for products. Mirrors carry Content-Type: text/markdown, X-Robots-Tag: noindex (duplicate-content protection) and Cache-Control: no-cache (cache-plugin compatibility precedent); per-post transients are self-invalidating via a post_modified_gmt key hash, so no invalidation hooks are needed
* New - ACP / ChatGPT Shopping feed readiness (WooCommerce stores): shop_to_llm_acp_feed_readiness() audits the live catalog (latest 100 published products, same query shape as the XML feed) against the five fields OpenAI's discovery-first shopping experience reads — title (present, ≤150 chars), description (present, ≤5000 chars), price (>0), availability (in-stock), image (featured asset) — plus GTIN as the recommended field. Score 0-100 = 0.9 × average required-field pass rate + 0.1 × GTIN coverage (mirrors the cloud dashboard formula), ready threshold ≥80. Renders as a fourth card in the existing activation proof strip (same markup/classes, 'package' icon, "ACP N/100" live badge; gap text lists up to three concrete fixes e.g. "Fix: 3 missing images, 2 missing prices to raise your ACP score") — only on WooCommerce sites, only when products exist; hourly transient invalidated on save_post_product and woocommerce_update_product alongside the product-quality cache. Readme FAQ documents the honest path: merchants apply at chatgpt.com/merchants, no plugin can guarantee a listing
* New - IETF MCP discovery manifest at /.well-known/mcp-server (draft-serra-mcp-discovery-uri-04): agents resolving a bare domain can now discover the site's MCP endpoint without out-of-band configuration. Manifest per spec §6.13/§6.14 — required fields mcp_version ("2025-06-18", synchronized with the MCP initialize default), name, endpoint (rest_url('shop2llm/v1/mcp'), host matches retrieval host per §6.8), transport "http" (spec's value for JSON-RPC-over-HTTPS); recommended fields description, capabilities ["tools"], trust_class "public", auth {required, apikey} (mirrors the real Bearer-token posture), languages (from site locale), docs, last_updated, expires (+7 days), cache_ttl 3600. Served with Content-Type: application/json, X-Robots-Tag: noindex, Cache-Control: public, max-age=3600, hourly transient cache; reachable three ways — dedicated rewrite rule (^\.well\-known/mcp\-server$, registered on init and in the deferred activation setup), template_redirect query-var renderer, and the parse_request URI fallback (dot-directories are shadow-prone on some hosts, the fallback wins the race)
* Improvement - AI usage policy upgrades from comment-only to the standard Content-Signal directive (contentsignals.org): the robots.txt section now appends a machine-readable "Content-Signal:" line mapped from the existing three modes — open → ai-train=yes, search=yes, ai-input=yes; attribution → ai-train=no, search=yes, ai-input=yes; closed → ai-train=no, search=no, ai-input=no — while the human-readable comment banner stays untouched; still opt-in and off by default
* Docs - readme.txt: two new FAQ entries ("How do I get my products into ChatGPT shopping?" — ACP readiness + chatgpt.com/merchants with an explicit no-guarantee disclosure; "Does Shop2LLM serve Markdown versions of my pages to AI agents?"), the crawler-controls FAQ now mentions the Content-Signal directive, and the free-feature list gains the Markdown-mirror and ACP-readiness bullets
